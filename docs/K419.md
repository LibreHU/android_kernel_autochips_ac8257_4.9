# Noyau 4.19.325 experimental (branche `experimental-4.19.325`)

**EXPERIMENTAL : pas encore teste sur l'unite.** Le noyau de tous les jours reste celui de `stable-4.9.337`
(release `latest-stable-4.9.337`, OTA). Cette branche n'alimente ni l'OTA, ni LibreHU Apps, ni
LibreHU-flashablesZips : sa CI publie seulement une prerelease `latest-experimental-4.19.325` marquee
experimentale.

## Pourquoi 4.19.325
- 4.19 est la branche longue duree suivante apres 4.14 ; sa derniere version upstream est **4.19.325**
  (5 decembre 2024, fin de vie de la branche chez kernel.org).
- La branche reste maintenue par le projet CIP (Civil Infrastructure Platform) jusqu'en 2029 (versions
  `4.19.325-cipNNN`), sans les correctifs Android.
- Le coeur vient de l'Android Common Kernel `deprecated/android-4.19-stable` (meme 4.19.325) : binder, ashmem,
  ION, sync, cpufreq / schedtune et les correctifs Android de 4.19.

## Comment l'arbre a ete construit
1. Coeur = ACK 4.19.325.
2. Delta vendor = `autochips-gpl` (AutoChips AC8257, Linux 4.9.117) contre l'ACK `android-4.9-p` le plus proche
   (`e05c16c16`) : fichiers vendor ajoutes tels quels, fichiers du coeur modifies par AutoChips fusionnes a 3 voies
   (base ACK 4.9, ours AutoChips, theirs ACK 4.19), conflits resolus un par un.
3. Modifications LibreHU de `stable-4.9.337` rejouees (KernelSU Next, tactiles, batterie, rc-jancar, cpufreq,
   USB, configfs, boost USB coupe, boost tactile, etc.).
4. Pilotes MediaTek / AutoChips portes sur les API 4.19 (voir plus bas). La pile eMMC (coeur MMC + hote ComboA)
   reprend le portage 4.19 de MediaTek pour MT6765 (arbre `gta7lite/android_kernel_samsung_mt6765`), avec le
   dossier plateforme `ac8257` d'AutoChips.

## Couche de compatibilite pour les pilotes ecrits pour 4.9
- `include/linux/librehu_compat_4_9.h` : en-tetes et macros que les pilotes vendor recevaient en 4.9
  (decoupage de `<linux/sched.h>` en 4.11, `DRIVER_ATTR`, `cputime64_t`, `ACCESS_ONCE`...). Force par `-include`
  dans les Makefile des dossiers vendor seulement, jamais dans le coeur.
- `kernel/librehu_cpu_notifier.c` + `include/linux/librehu_cpu_notifier.h` : les notifiers CPU de 4.9
  (`register_cpu_notifier()`, `CPU_ONLINE`, `CPU_DOWN_PREPARE`...), supprimes en 4.10, reconstruits sur deux etats
  cpuhp dynamiques (preparation sur le CPU de controle, en ligne sur le CPU lui-meme), avec les annulations
  (`CPU_UP_CANCELED`, `CPU_DOWN_FAILED`) et les variantes `_FROZEN` de la mise en veille.
- `include/linux/timer.h` (sous `CONFIG_MEDIATEK_SOLUTION`) : `setup_timer()`, `init_timer()`, `.data` et
  `DEFINE_LEGACY_TIMER()` de 4.9 par un trampoline (`.legacy_function`).
- `kernel/librehu_compat_4_9.c` : fonctions du printk MediaTek 4.9 sans effet en version user (comme en 4.9).

## Pile eMMC / carte SD (ComboA)
Le pilote hote MSDC et le coeur MMC sont ceux du portage 4.19 de MediaTek (MT6765). Les changements d'AutoChips
de leur noyau 4.9 y ont ete reportes, pour garder le comportement du noyau d'origine :
- cache de l'eMMC laisse eteint (`CONFIG_ATC_EMMC_CACHE_SUPPORT` non active, comme en 4.9 : certains eMMC ont
  des bugs avec le cache) ;
- pas de file de commandes (CMDQ) en mode recovery, comme le noyau MediaTek / AutoChips 4.9 ;
- source d'horloge des hotes choisie a la sonde (`msdc_select_clksrc()`), coupee pendant la veille ;
- reglages des hotes lus dans la metazone quand une entree existe (`CONFIG_MSDC_ATC_MMC_DEBUG`) ;
- carte SD : 3 essais par frequence, horloge divisee apres 3 echecs, carte abandonnee apres 8 (jusqu'au retrait),
  retrait detecte sur timeout CMD13, relecture du SCR des cartes qui se disent SD 1.0, nouvelle detection apres
  chaque interruption de detection, aucun scan pendant l'extinction ;
- pas de mise en veille runtime des hotes ni de la carte SD (`CONFIG_ATC_SD_RUNTIME_SUSPEND_SUPPORT` non active) ;
- cycle d'alimentation de l'eMMC apres un reset materiel, re-accord aussi sur timeout de donnees, pas de re-accord
  sur une violation de protection en ecriture.

Non reporte (sans effet sur l'UJC201) : la protection en ecriture logicielle `MMC_ATC_SW_WP` (le fichier debugfs
qui l'active n'est pas cree sur Jancar, deja en 4.9), les commandes d'ingenierie 33 a 36 de `/proc/msdc_debug`
(changer horloge / largeur de bus a chaud et les sauver en metazone), l'histogramme de latence AutoChips.

## Demarrage (system-as-root)
- En demarrage normal le LK passe `skip_initramfs`, et `dm="... verity ..." root=/dev/dm-0` quand le vbmeta
  verifie system (vbmeta stock). Ces deux parametres des noyaux Android 4.9 n'existent plus dans l'ACK 4.19 : ils
  sont repris tels quels (`init/initramfs.c`, `init/do_mounts_dm.c`, `dm_ioctl_export()` de `drivers/md/dm-ioctl.c`).
  Les partitions de l'eMMC apparaissant de facon asynchrone, `dm=` attend jusqu'a 10 s les peripheriques qu'il nomme
  (`PARTUUID=...`).
- vbmeta en `--disable-verity` (drapeaux 1) ou `--disable-verification` (drapeaux 3) : le LK passe
  `root=PARTUUID=...` (system monte sans dm-verity). Sans `rootwait`, le noyau attend jusqu'a 10 s cette partition
  (l'eMMC est detectee de facon asynchrone), puis echoue comme avant.
- `Image.gz-dtb` (DTB concatene au noyau, l'image boot de l'UJC201 n'a pas de DTB separe) : regles de construction
  reprises de 4.9 (`arch/arm64/boot/Makefile`).

| Liens automatiques entre peripheriques du DT (`of_devlink` de l'ACK : un consommateur attend que ses fournisseurs aient un pilote) | absents | desactives par defaut, comme en 4.9 (`of_devlink=1` les remet) : voir « Premier essai sur l'unite » |

## Corrections faites au passage (bugs du code vendor)
- `domain->iova_cookie` lu comme une `iova_domain` dans `pseudo_m4u` : faux des 4.11 (le cookie commence par
  son type) ; accesseur `iommu_dma_get_iovad()` ajoute.
- Gestionnaires `fault` qui renvoyaient `-1` (tous les bits `VM_FAULT_*`, dont `VM_FAULT_OOM`) ou `NULL`.
- Tactiles : `snprintf(..., PAGE_SIZE, ...)` vers des tampons de 25 / 128 octets (focaltech), allocation non
  verifiee (`touchscreen_cust.c`), casts de pointeurs 64 bits vers des entiers 32 bits (AutoChips di / vdp,
  metazone, wch).
- RNDIS : longueurs de l'hote verifiees (somme sur 64 bits, message plus court que son en-tete).
- `mount()` « stockage plein » d'AutoChips : verifie maintenant les droits de montage et ne fuit plus memoire.

## Premier essai sur l'unite (15/11/2026, methode recovery)
- Resultat : redemarrage immediat. `console-ramoops` (pstore) : oops a 0,22 s dans `hal_btif_info_get()` appele par
  `BTIF_init()` (pilote BTIF du Bluetooth MediaTek), lecture a l'adresse `0x2f8` (pointeur NULL + decalage de
  `of_node`), puis « Kernel panic - not syncing: Fatal exception » et reboot par le watchdog.
- Cause : `of_devlink` de l'ACK 4.19 (actif par defaut, `drivers/of/property.c`) cree un lien entre chaque noeud du
  DT et ses fournisseurs (`clocks`, `pinctrl-*`, `power-domains`, `iommus`...) : 117 lignes « Linked as a consumer »
  avant l'oops, dont 32 vers `10001000.infracfg_ao`. Un consommateur ne peut etre sonde qu'une fois ses fournisseurs
  lies a un pilote ; or les fournisseurs d'horloges MediaTek (`infracfg_ao`, `topckgen`, `apmixed`) sont declares par
  `CLK_OF_DECLARE_DRIVER` (`drivers/clk/mediatek/clk-ac8257.c`) : ils ont un peripherique de plateforme mais aucun
  pilote ne s'y lie jamais, leurs consommateurs restent differes pour toujours. `BTIF_init()` suppose que sa sonde
  s'execute dans `platform_driver_register()` et lit ensuite le peripherique qu'elle aurait enregistre
  (`g_btif[0].private_data`), reste a NULL. Le 4.9 n'a pas ces liens.
- Correction : `of_devlink` desactive par defaut (ordre de sonde du 4.9) ; `BTIF_init()` abandonne proprement (BTIF
  desactive, `-ENODEV`) si sa sonde n'a pas eu lieu, au lieu de faire planter le noyau.
- Aussi dans ce journal, sans effet bloquant et deja presents avec le DT stock : « irq: type mismatch, failed to map
  hwirq-189 for intpol-controller@10200a80 » (SPI 189 declaree deux fois dans `ac8257.dts`, en niveau bas puis en
  front montant) et un avertissement de `gic_irq_domain_translate()` (interruption du DT sans type ; 4.19 le signale,
  4.9 non).
- QEMU ne pouvait pas le voir : la machine `virt` n'a pas les noeuds MediaTek, et `BTIF_init` y etait saute
  (`initcall_blacklist`).

## Essais suivants sur l'unite (15/11/2026)
- **Essai 2** (r157, correctif ci-dessus) : BTIF passe ; oops a 0,358 s dans `alloc_iova()` appele par
  `pseudo_probe()` (`pseudo_m4u`) : domaine IOVA jamais initialise (« granule 0x0, start_pfn 0x0 »).
  Corrige par `a45990f` (fait par l'utilisateur) : `CONFIG_ARM64_DMA_USE_IOMMU=y` (integration DMA / IOMMU de
  MediaTek pour arm64, dans l'arbre) ; essai 4 : « granule 0x1000 », `pseudo_m4u` sonde.
- **Essai 4** (`a45990f`, `initcall_debug ignore_loglevel`) : le journal s'arrete a 3,41 s, sans oops, pendant
  `_mt_cpufreq_pdrv_init` (seul initcall commence et jamais fini). Deux causes trouvees :
  - **Sondes repoussees a `late_initcall`** : pendant le peuplement du DT, l'ACK 4.19 met `fw_devlink` en pause
    (`fw_devlink_pause()`, `drivers/of/platform.c`), et pendant cette pause chaque nouveau peripherique est mis en
    attente de fournisseurs, meme avec `of_devlink` coupe. Les pilotes deja enregistres (`1000b000.pinctrl`,
    `10007000.toprgu`, `10207000.devapc`, `10219000.emi`, `1022a000.dramc`, `10238000.gce_mbox`, `10440000.sspm`)
    echouent alors leur premiere sonde (`-EPROBE_DEFER`, « returned -517 after 0 usecs », sans entrer dans le
    pilote) et ne sont resondes qu'a `deferred_probe_initcall` (0,37 s). Trop tard : `sspm_module_init` (0,253 s)
    echoue (« SSPM: logger IPI fail ret=-101 », « [SSPM] Platform Init Failed »), le PMIC aussi
    (« pmic_ipi_to_sspm ap_ret_w = -101 »), et cpufreq, qui passe par le SSPM, ne finit pas. Correction : pas de
    pause sans `of_devlink` (aucun lien n'est jamais cree) : ces peripheriques sont sondes pendant le peuplement,
    comme en 4.9.
  - **4 Gio de RAM perdus** : « Memory: 1670328K/6209656K available ... 4539328K reserved » contre
    « 5864028K/6209656K available ... 345628K reserved » en 4.9. Le LK ajoute la zone `zone-movable-cma-memory`
    (`0xc0000000`, `0xffc00000`) que la ZMC de MediaTek rend utilisable en 4.9 (« ZMC: zmc_memory_init ») ; sans
    elle, le code generique la garde reservee. Correction : `drivers/misc/librehu/zmc_release.c` la rend au
    noyau (chemin « Abort reserve memory » de `zmc_memory_init()`) et `zone_sizes_init()`
    (`arch/arm64/mm/init.c`) en fait la zone `ZONE_MOVABLE`, comme la ZMC du 4.9 : `ZONE_DMA32` s'arrete a sa base
    (`0xc0000000`), les allocations du noyau restent dessous, et seules les pages des processus et du cache vont
    au-dessus (une partie est au-dela de 4 Gio : des pilotes vendor qui donnent des adresses physiques a du
    materiel 32 bits casseraient avec des allocations noyau la-haut). Verifie dans QEMU avec un DTB portant ce
    noeud : « DMA32 zone: 524288 pages », « Movable zone: 262144 pages », espace utilisateur atteint ; sans le
    noeud, rien ne change. `3961b82` (fait par l'utilisateur) : les tables du M4U (io-pgtable v7s) acceptent les
    adresses physiques sur 34 bits avec le quirk `MTK_4GB`, au lieu de refuser tout ce qui depasse 4 Gio.
- Vu dans les memes journaux, a revoir si cela persiste apres ces corrections (probablement des consequences du
  SSPM / PMIC injoignables) : regulateurs `vcama` / `vcamd` (« failed to get current voltage(-1) »),
  `register_cpufreq_notifier` (-22). `dma_init_reserved_memory` (-12) est normal sans zone DMA par defaut.

## Audit du 15/11/2026 (journal de l'essai 4, `initcall_debug`, et configurations 4.9 / 4.19 comparees)
Ecarts reels avec le 4.9, corriges : `of_devlink` (BTIF), pause `fw_devlink` (pinctrl, SSPM, PMIC, CMDQ de
l'affichage, cpufreq), zone ZMC de 4 Gio (voir ci-dessus), `enable_irq()` avant `request_irq()` dans `jpeg_probe`
(« WARNING at irq_startup » en 4.19 : la ligne demarree sans gestionnaire), et `a45990f` pour `pseudo_m4u`.

Verifie et identique au 4.9 (pas une regression, rien a changer) :
- « CPUn: Unknown IPI message 0xf » : aussi dans le dmesg du 4.9 sur l'unite.
- `11000680.dma-controller` (DMA des UART) : le pilote attend 8 canaux, le DT en decrit 4 : `-ENODEV`, meme code et
  meme DT en 4.9.
- `otg_iddig` (-22) : le noeud n'a pas d'interruption, dans les deux DT.
- « irq: type mismatch, failed to map hwirq-189 » : SPI 189 declaree par `dualarm` (niveau bas) puis par `utos`
  (front montant, TEE Microtrust absent) ; `dualarm` garde la sienne. WARN de `gic_irq_domain_translate` : interruption
  de `toprgu` declaree `IRQ_TYPE_NONE` (4.19 le signale, 4.9 non).
- Messages trompeurs du code vendor : « node 'mediatek,ac8257-mcdi' can not iomap! » et « ion_init fd register notifer
  fail » s'affichent quand l'operation REUSSIT (conditions inversees, memes sources en 4.9).
- Tas ION `system_contig` desactive par le code vendor, ABI ION a handles de MediaTek conservee (vendor Android 9).
- Carte SD (`msdc1`) : reprise en sonde differee (« externdevice ») ; eMMC (`bootdevice`) et USB (`mt_usb`) sondes.
- `register_cpufreq_notifier` (-22, `arch_topology`) : pas de `capacity-dmips-mhz` dans le DT (un seul cluster).
  `cacheinfo_sysfs_init` (-2), `integrity_fs_init` (-19), `conn_md_init` (-1, pas de modem), `scp_init` (-1 en
  demarrage recovery, memoire SCP gardee hors de Linux) : attendus.
- Configurations : meme DDK GPU (RGX), TEE Trusty, HZ 250, `PREEMPT`, VA 39 bits, eBPF de netd (`BPF_SYSCALL`,
  `CGROUP_BPF`, `xt_bpf` ; Android 9 n'utilise plus `xt_qtaguid` avec `first_api_level` 28), dm-crypt / verity,
  `slub_debug` / `page_owner` de la ligne de commande sans effet (non compiles dans les deux),
  `HARDENED_USERCOPY_FALLBACK` (une copie hors liste blanche avertit au lieu de planter). Options du 4.9 absentes
  ici et sans autre effet : modem CCCI, AEE, outils de debogage MediaTek, ordonnanceur HMP / `schedplus`.

Audit multi-agents du 15/11 (relecture statique, chaque constat reverifie avant correction) :
- cpufreq / SSPM : l'echec de l'IPI de la table OPP (`IPI_DVFS_INIT_PTBL`) etait ignore et le DVFS du SSPM
  demarrait quand meme (blocage plausible de l'essai 4) : sans table, plus de pilote cpufreq, les CPU restent a la
  frequence de demarrage ; retours de `mt_cpufreq_dts_map()` et `cpuhvfs_module_init()` verifies ; boucle de
  lecture du journal du SSPM bornee (debordement de `log_box_parsed[]`, lecture de l'index -1) ; delai de l'IPI en
  scrutation (`retries == 0` au lieu de `< 0` : vrai delai non detecte, succes au dernier essai pris pour un delai
  puis `BUG_ON`) ; sonde SSPM qui peut etre reessayee (`-EPROBE_DEFER` garde).
- Regulateurs inutilises coupes juste apres `late_initcall_sync` comme en 4.9, et non 30 s plus tard sous des
  pilotes vendor qui allument des LDO par ecriture directe dans le PMIC.
- GIC (`MTK_GIC_TARGET_ALL`) : affinite effective mise a jour (« did not update eff. affinity mask »).
- `CONFIG_ARCH_NR_GPIO=512` comme en 4.9 (l'ACK 4.19 met 256 : tous les numeros GPIO globaux, `/sys/class/gpio`,
  etaient decales de 256).
- Non corriges : pilote goodix amont sur le noeud `ctp@01` (le dtbo stock, absent du depot, dira s'il touche les
  broches du GT928) ; sonde CMDQ sans GCE (declencheur supprime par `b584a44`). Lenteur de 2,4 s de l'essai 4 :
  reaffichage du tampon `initcall_debug` sur la console UART a 921600 bauds, pas l'eMMC ni l'affichage.

Suite de l'audit (agents compat, besoins d'Android, optimisations), corrige ici :
- `mtk_ts_wmt.c` (thermique Wi-Fi, compile) : son minuteur remplacait le trampoline de la couche de compatibilite
  (`.function = (void *)wmt_cal_stats`) et recevait le `struct timer_list *` au lieu de ses donnees : il ecrivait
  dans la liste du minuteur puis `add_timer()` tombait sur `BUG_ON(timer_pending())` des que le Wi-Fi envoyait des
  donnees (panique sous Android). Passe par `legacy_function` ; meme correction dans `mtk_ts_pa.c` (non compile).
- KernelSU : journal « su » (desactive par defaut) qui lisait un `struct user_arg_ptr *` comme un `argv[]` noyau
  (oops) et ne copiait jamais l'argument ; `free_mark` absent des `fsnotify_ops` (appel NULL au-dela de 4.12).
- `do_mounts_dm.c` : `uuid` non initialise pour une valeur autre que « none » (identique en 4.9, pas atteint ici).
- Erratum Cortex-A53 835769 : le CPU est r0p4 (`410fd034`), le contournement du compilateur n'etait pas actif
  (clang ne l'active d'office que pour les cibles Android) : `-mfix-cortex-a53-835769` dans `arch/arm64/Makefile`.

## Essai 5 : premier demarrage d'Android (15/11/2026, r164 `1acff0e`)
- Resultat : LineageOS 16.0 demarre jusqu'au bout sur le 4.19 (`sys.boot_completed=1`), 5,7 Gio vus (`MemTotal`
  5981120 kB, `ZONE_MOVABLE` depuis `0xc0000000` comme le ZMC du 4.9), aucun peripherique differe
  (`devices_deferred` vide). Journaux pris par `adb root` (dmesg, logcat, getprop, dumpsys, tombstones) et un
  `bugreport` d'un second demarrage. Cette image n'avait pas encore les corrections de `1a4061b` (r165).
- IOMMU (M4U) : 1067 avertissements `__arm_v7s_map` (`-EEXIST`, une PTE deja presente au niveau 2), toujours a la
  meme IOVA pour un processus (0x5b700000, 0x5af00000...), a partir de la fin de l'animation de demarrage : couches 1
  et 2 de l'affichage desactivees (« no valid mva »), blit MDP en echec (« get input memory hardware base failed »),
  arret du composer HWC, donc redemarrage de SurfaceFlinger et de zygote (63,8 s). Causes, trouvees en comparant au
  4.9 et au noyau MediaTek 4.19 de reference (MT6765) :
  - depuis 4.11, `iommu_dma_map_sg()` prend l'IOVA dans des caches par CPU (`alloc_iova_fast()`) qui supposent des
    plages arrondies a une puissance de deux et rendues avec la meme taille ; les tampons a adresse fixe du pilote
    `pseudo_m4u` (`alloc_iova()` de taille quelconque) y retournaient par `iommu_dma_unmap_sg()` et pouvaient en
    ressortir plus grands, par-dessus des mappages encore utilises ;
  - un echec de `iommu_dma_map_sg()` laisse `sg_dma_address()` a 0 en 4.19 (`IOMMU_MAPPING_ERROR`) ; le pilote
    attendait `DMA_ERROR_CODE` (~0) : le tampon recevait la MVA 0 (puis « sg have not been added ») ;
  - `alloc_iova()` d'une adresse fixe part, depuis 4.15, du dernier noeud alloue et tombait en dessous : zones
    reservees ISP (`0x76000000`) et IHM camera de recul de l'ARM2 (`0x77400000`) mappees a 0x5f400000 et 0x61306000
    au lieu de 1:1.
  Corrections (`pseudo_m4u_v2.c`, `iova.c`, `io-pgtable-arm-v7s.c`) : l'IOVA du pilote vient de l'arbre et y
  retourne, comme en 4.9 (`alloc_iova()` alignee ; demappage de toute la plage puis `__free_iova()`), jamais par les
  caches ; un echec est vu comme tel ; une plage a adresse fixe se cherche depuis le haut de l'arbre (comme les
  noyaux MediaTek 4.19) sans deplacer le noeud en cache ; l'avertissement `-EEXIST` de `io-pgtable-arm-v7s.c` une
  seule fois (chaque trace a 921600 bauds bloquait l'appelant), et le pilote journalise chaque echec (avec une
  limite), avec la premiere page deja mappee de la plage et son adresse physique.
- ramoops : aucun `console-ramoops` apres un demarrage 4.19. Le `fs/pstore/ram.c` MediaTek 4.9 a une seconde zone
  console (`bprz`) apres la console ; sans elle, la console 4.19 tombait dans cette zone, et la console 4.9 (la ou
  ecrit aussi `ac8257_early_pstore_console`, `0x47cdf000`) dans la zone des dumps 4.19, effacee a chaque demarrage
  (« persistent_ram: found existing invalid buffer, size 208406 »). Corrige : memes zones qu'en 4.9.
- Stockage : `/system/bin/sdcard` s'arrete (« failed to sdcardfs_setup » ; `mount` de sdcardfs : « No such
  device »). Le `sdcard.cpp` d'Android 9 ne sait plus que monter sdcardfs (« The older FUSE-based design that used
  to live here has been completely removed ») et la ROM met `ro.sys.sdcardfs=1` : sans sdcardfs, `/sdcard` n'est
  pas monte. sdcardfs demande les crochets VFS par montage (`permission2`, `setattr2`, `notify_change2`, `vfs_*2`)
  retires de l'ACK 4.19 : portes le 16/11 (voir le tableau des differences).
- Wi-Fi / BT / GPS / FM : `/vendor/lib/modules` contient les modules du 4.9 (« wmt_drv: disagrees about version of
  symbol module_layout ») : pas de `/dev/wmtdetect`, le HAL Bluetooth s'arrete (« TurnOn: failed to init
  Bluetooth! »). Il faut le module KernelSU `librehu_connectivity_ksu.zip` de la meme prerelease ; `ksud` manquait
  dans `/data/adb` (`ksud post-fs-data` : code 127) : l'appli KernelSU Next l'installe quand on l'ouvre.
- Camera de recul : `backcar` demandait un GPIO absent du DT (`backcar_mcu_notify_gpio`, -2 ; meme chose en 4.9) :
  ignore maintenant. Aucun decodeur TP2850 / TP2854 / TP9963 ne repond en I2C (`i2c-0`, 0x44) : a comparer avec un
  journal 4.9.

    `iommu_map()` rate) ;
  - sinon il n'efface que les blocs entiers du niveau et rend quand meme toute la taille : le reste reste mappe
    alors que son IOVA est rendue, d'ou les `-EEXIST` des mappages suivants au meme endroit (essai 5 ; l'hypothese
    des caches d'IOVA n'etait pas la bonne, les corrections de l'essai 5 restent valables).
  Correction : `arm_v7s_unmap()` demappe taille de page par taille de page (`iommu_pgsize()`), comme `iommu_map()`
  mappe.

## Plantage du noyau dans boot (16/11/2026) : MCDI et PSCI
- Symptome : depuis la partition boot, Android s'arrete net vers 10-12 s (rien dans pstore apres la ligne
  « MCDI bootup check: PASS »), l'unite redemarre ; depuis recovery, aucun probleme. expdb (journaux LK /
  preloader) : `[pmic_check_rst] Cold Reset`, `POFFSTS 0x20`, `kedump: last is full pmic reset!`,
  `wdt_status 0x800`, `exp_type 0x0`, `boot_reason=4` : reset complet par le PMIC, sans exception Linux. Meme
  signature que le noyau 4.9 de la branche `reverse-engineering` en partition boot.
- MCDI (veille profonde des coeurs) ne s'active qu'en demarrage normal : le LK n'y charge le micrologiciel SPM
  qu'en demarrage normal (cf. SPM/SCP, `recovery_mem.c`). Son premier passage (`BOOT_TIME_LIMIT` = 10 s)
  precede le reset de ~1 s dans les deux plantages releves.
- Cause : `psci_cpu_suspend_enter()` de l'ACK android-4.19 prend un parametre PSCI deja calcule, alors que le
  cpuidle MediaTek (`mtk_enter_idle_state()`, `arm_cpuidle_suspend(index)`) passe un index d'etat. MCDI
  demandait donc a l'ATF l'etat `0x2` (veille sans perte de contexte, point d'entree 0) au lieu de `0x10001`
  (coeur eteint, table `arm,psci-suspend-param` du device tree). Correction : retour a la version 4.9 /
  reference MediaTek 4.19 (index -> `state[index - 1]`). Touche aussi SODI, deep idle et la mise en veille
  (`MTK_SUSPEND_MODE`).

## SELinux permissif dans les images boot (16/11/2026, r174)

- Correction : `boot_ac8257.img` et `boot_ac8257_bootmenu.img` de la CI ajoutent `androidboot.selinux=permissive`

## Analyse complete du demarrage r175 (16/11/2026, partition boot, Permissive)
Journaux : dmesg en direct (0-238 s), journaux LibreHU, bugreport (session de 4 min). Correctifs valides par ce
demarrage : PSCI/MCDI (`ba7e90c`, l'unite demarre depuis boot), SELinux permissif (`ba3d841` : batterie factice
vue par Android, MCU sur ttyS1, puce MFi, Bluetooth actif).

Problemes confirmes (cause trouvee) :
1. **Demarrage bloque 30 s** : `MakeNetworkPolicyServiceReady took to complete: 30001ms`,
   `IllegalStateException: Service NetworkPolicy init timeout`. Android 9 n'active le controle de bande passante
   que si `/proc/net/xt_qtaguid/ctrl` existe ; sinon `NetworkPolicyManagerService.initService()` rend la main sans
   liberer son verrou et `systemReady()` attend 30 s. Le noyau 4.9 a `CONFIG_NETFILTER_XT_MATCH_QTAGUID=y` ;
   l'ACK 4.19 n'a plus `xt_qtaguid`. Effets : animation de demarrage et interface en retard (tactile « lent a
   venir »), statistiques de donnees absentes.
2. **Programme eBPF de netd refuse** : `bpfloader: load cgroup_ingress_prog failed: Invalid argument`, verificateur
   4.19 : « At program exit the register R0 has value (0x0; 0xff) should have been in (0x0; 0x1) » (controle du
   code de retour des programmes cgroup skb, absent en 4.9).
3. **ksud ne s'execute pas** (`init: cannot execve('/data/adb/ksud'): Permission denied`,
   `op=security_bounded_transition seresult=denied oldcontext=u:r:init:s0 newcontext=u:r:ksu:s0`) meme en
   Permissive : /data est nosuid, la politique Android 9 n'a pas la classe `process2`
   (`nnp_nosuid_transition=0`), seule une transition bornee est permise. Les scripts post-fs-data / service des
   modules KernelSU ne tournent pas ; `/metadata/ksu/modules.rc` absent (pas de partition metadata).
4. **Tas ION `ion_system_contig_heap` non cree** (`ion_mtk_heap_create: error creat heap ion_system_contig_heap
   type 1`) et `COMPAT_ION_IOC_FREE unlocked_ioctl fail` (liberation ION d'un processus 32 bits) : a comparer au 4.9.

A verifier :
- `irq: type mismatch, failed to map hwirq-189` : le noeud `utos` (front montant) et `dualarm` (niveau bas)
  declarent la meme interruption 189 dans le DT stock ; dualarm fonctionne (`dualarm_bcar_isr_handler` appele).
- `[DISP][LCM] interface_read_byte: interface_client NULL!` (x35) : lecture du pont LVDS (I2C 0x2d) avant que son
  client I2C soit pret.
- `Netd: invalid interface index: wlan%d(0)` : evenement reseau du pilote Wi-Fi avant le nommage de l'interface.
- Plantages vus dans les pierres tombales des demarrages precedents : `media.codec` (omx, SIGSEGV en rafale),
  Firefox `SIGILL ILL_ILLOPC` dans `libdexfile.so` (code systeme : corruption memoire possible), Bluetooth
  `TurnOn: failed to init Bluetooth!` (pas dans ce demarrage : Bluetooth actif).
- Heure : le systeme part du 15/11 03:06, puis 01/01/2000, puis l'heure reseau (RTC a zero).

Bruit sans consequence (aussi attendu en 4.9) : NACK I2C 0x10/0x11 sur les bus 0 a 5 (recherche de la puce MFi,
trouvee sur i2c-6), cameras TP28xx absentes (0x44), Goodix-TS (le tactile est le GT928), regulateurs camera
factices, tas ION securises non pris en charge, agps sans modem, `storageproxyd` sans RPMB.

## Deux variantes : a9 (Android 9) et a10 (Android 10 et plus) (16/11/2026)
La CI compile le meme arbre deux fois (`arch/arm64/configs/ac8257_a9.config` / `ac8257_a10.config` par-dessus le
defconfig) ; chaque fichier de la release porte le suffixe `_a9` ou `_a10`, et les modules ne marchent qu'avec le
noyau de la meme variante (`uname -r` = `4.19.325-a9` / `4.19.325-a10`).

| | a9 (LineageOS 16.0, stock) | a10 (LineageOS 17.1...) |
|---|---|---|
| `xt_qtaguid` | oui (remplace `xt_owner`, comme en 4.9) | non (comptage par eBPF, comme les noyaux communs Android) |
| `xt_owner` | non | oui |

## Limite connue : matrice de compatibilite d'Android 9
